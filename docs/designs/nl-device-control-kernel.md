## Problem Statement

发起人希望公司有一个统一的软件平台，接入大疆设备和基于 ROS2 的机器人，并能接入 CV 模型和大模型 API，从想法做到落地交付，之后在内部推广或商用，并争取产生专利。

本次会话把范围收窄为一个具体功能：**用户输入一句自然语言（第一版为文字，语音随后），系统把它变成设备指令并安全地执行。** 平台不是第一版的交付物，而是从这个功能里抽出来的结构。

## Demand Evidence

目前没有外部需求证据。被问到"最近谁因为缺这个平台吃了亏"时，发起人没有给出具体的人或事，给出的动机是：自己有大疆设备、想基于平台开发插件、想推广、想产生专利。

这属于"先有方案，再找问题"。它不否定项目，但意味着第一版的首要目的是尽快做出可以拿给具体的人看的东西，用他们的反应补上这块证据。

## Status Quo

- 公司内部没有统一的设备接入平台，各项目各自对接设备。具体谁在对接、花了多少时间，本次会话没有得到数据。
- 行业内已有的开源件（网络检索，2026-11-12，只读摘要，未核实代码）：
  - 大模型 + ROS2：ROSA（NASA JPL）、RAI（RobotecAI）、ROS-MCP 服务器。
  - 大疆 + ROS2：psdk_ros2，仅支持带 Payload SDK 的行业机（M30、M300 RTK、M350 RTK）。
  - 自然语言控制无人机：PX4 + ROS2 + 本地模型的开源智能体，指令格式全部合法，但任务成功率最高 40%（arXiv 2506.07509；只读了检索摘要，未核实原文）。
- 公认的坑：把大模型当作安全层。2026 年 ROSClaw 论文报告，相同约束下不同模型的越界动作提议率相差可达 4.8 倍，执行层设计比提示词更影响安全（arXiv 2603.26997；只读了检索摘要，未核实原文）。

## Premises

1. 先做插件，不先做平台。第一个交付物是"自然语言控制设备"这一个功能。
2. 不重造轮子。ROS2 侧将来复用现成智能体框架，大疆行业机侧复用 psdk_ros2；自己写的只有中间的翻译与校验层，以及现有方案没覆盖的设备适配。
3. 大模型不直接驱动设备。每条指令都经过独立的校验层才能到达设备。这一层是产品核心。"校验层独立于大模型"这个思路本身已是公开做法，不构成专利点；如果有可专利的内容，只会是这一层内部某个尚未确定的具体技术做法，需专利代理人检索后判断。
4. **以 Osmo Pocket 3 为第一验证载体。**（发起人决定。原提议是以 ROS2 仿真为主、Pocket 仅作演示，被否决。保留意见：非官方协议、无云台控制、设备层代码不能迁移到无人机、不能作为商用基础。对策见"Recommended Approach"中的适配器隔离。）
5. 先内部用，商用推迟到有第一个真实用户之后。

## Approaches Considered

### Approach A: Pocket 3 直连演示
一个命令行程序把大模型输出直接接到 node-osmo。未选：指令、校验、设备代码混在一起，换设备等于重写，且没有不依赖硬件的自动测试。

### Approach B: 设备无关的指令内核 + 适配器（已选）
见下节。

### Approach C: MCP 服务器
把 Pocket 3 的能力包装成 MCP 工具，由第三方大模型客户端充当自然语言入口。未选：依赖第三方客户端，难以作为独立产品交付，自己掌握的日志和控制较少。可在将来作为内核的另一个前端加入。

## Recommended Approach

三层结构，层与层之间只通过明确定义的数据格式通信。

```
  文字输入（之后加语音）
          |
          v
  +-----------------+
  |      前端       |   命令行；语音转文字放在第三个里程碑
  +-----------------+
          |  一句话
          v
  +-----------------------------------------------+
  |                    内核                        |
  |  1. 翻译：大模型按设备能力清单，把话转成        |
  |     计划 / 需要澄清 / 无法执行 三种结果之一     |
  |  2. 校验：动作是否在允许清单内、参数是否在      |
  |     范围内、当前设备状态是否允许、"开始直播"    |
  |     是否已经人工确认                           |
  |  3. 记录：原话、翻译结果、校验结论、执行结果    |
  |     逐条写入日志                               |
  +-----------------------------------------------+
          |  通过校验的指令
          v
  +-----------------+     +-----------------+
  | 适配器：模拟设备 |     | 适配器：Pocket 3 |   以后：psdk_ros2、ROS-MCP
  +-----------------+     +-----------------+
```

关键设计决定：

- **语言与运行环境**：TypeScript + Node.js。原因是 node-osmo 本身是 TypeScript 库，同一语言可以直接调用，不需要跨语言桥接。
- **适配器接口**：每个适配器实现三件事：声明自己支持哪些动作及参数范围（能力清单）、执行一条指令、报告当前状态。内核只认这个接口，不知道具体设备。
- **翻译的输出只有三种**，由大模型按能力清单生成：
  1. 计划：一个有序的步骤列表，每步是 `{动作, 参数}`。一句话可以对应多步。
  2. 需要澄清：附一个要问用户的问题。命令行把问题显示出来，用户的回答与原话一起重新翻译。澄清最多一轮；第二次仍需澄清则按"无法执行"处理。问题和回答记录在同一条日志的澄清字段里，不另起一行。
  3. 无法执行：附原因（例如设备不支持该动作）。
  模型可替换，在配置文件里指定并写入每条日志。
- **校验层独立于大模型**：纯代码规则，不调用模型。这是对"把大模型当安全层"这个公认错误的直接回应。
- **先全部校验，再执行**：整个计划的每一步都先在"推演状态"上校验（从当前状态出发，逐步套用前面各步的预期效果）。任何一步不通过，整个计划都不执行，并把是哪一步、为什么告诉用户。
- **第一版的校验规则（全部）**：
  - 动作必须在适配器的能力清单内，参数必须在清单声明的取值范围内。
  - 除"连接"外，所有动作要求"连接"字段为已连接。
  - "开始直播"要求"Wi-Fi"字段为已加入、"直播"字段为未直播，且本地配置里存在所指定的直播目标。
  - "设置直播参数"要求"直播"字段为未直播。
  - "连接"必须单独成为一个计划。一个计划里如果"连接"之后还有别的步骤，整个计划被拒绝，并说明原因：连接之后需要先确定直播状态，后面的步骤才能校验。用户先说"连接"，完成后再说后面的话。
  - 设备已连接时再次执行"连接"会被拒绝，提示已连接，不做任何事。
  - 规则所依赖的字段为"未知"时，该动作被拒绝，并告诉用户用哪个动作可以确定该字段（见下方"状态生命周期"）。不依赖未知字段的动作不受影响。
  - 需要人工确认的动作目前只有一个："开始直播"，因为它把画面发送到设备之外。其余动作不需要确认。确认机制是通用接口，以后接入能运动的设备时在此登记更多动作。
  - 确认的时机：整个计划全部通过校验之后、任何一步执行之前，只问一次。提示内容包括完整的步骤列表、将要推流的目标名称，以及一句明确说明："本工具目前无法停止直播，需要在相机上手动结束"（仅当适配器的能力清单里没有"停止直播"时显示）。用户输入 y 才执行；其他任何输入都视为拒绝，整个计划一步都不执行，日志记为"用户拒绝"。
  - 非交互运行：没有交互终端时默认视为拒绝。自动测试通过测试代码直接注入"同意"或"拒绝"来覆盖两条路径。容器演示只连接模拟设备，可用启动参数预先同意；该参数对真实设备适配器无效。
- **执行与失败处理**：步骤按顺序执行。适配器对每一步返回三种结果之一：成功、失败（附原因）、未知（超时或连接中断，无法判断设备是否已执行）。单步超时暂定 10 秒，按动作分别设置，作业跑出实际耗时后修订。不自动重试。某一步失败或未知时，停止后续步骤，不回滚已完成的步骤，并告诉用户哪些步骤已生效、哪一步出了问题、哪些没有执行。出现"未知"后各状态字段按下方"状态生命周期"表变化。
- **运行方式**：命令行是一个持续运行的交互会话，启动后一直接收输入，直到用户退出。状态保存在会话内存里，不是每句话启动一次进程。
- **设备状态**：第一版假定无法从设备读回状态（电量除外），由适配器维护一份"影子状态"，日志中标注每个字段的来源（推算值或人工告知值）。如果作业中核实到可以读回状态，改为以设备读回为准。
- **状态生命周期**：影子状态有四个字段。
  | 字段 | 取值 | 如何确定 | 何时变回未知 |
  |---|---|---|---|
  | 连接 | 已连接 / 未连接 | "连接"动作成功后为已连接。"连接"是适配器的一个动作，内部完成蓝牙连接和配对（对应能力表中的"配对"） | 程序启动时为未连接；蓝牙断开或任一步结果为"未知"时变为未连接 |
  | Wi-Fi | 已加入 / 未知 | "连接 Wi-Fi"动作成功后为已加入。该动作可重复执行 | 每次"连接"成功后重置为未知 |
  | 直播 | 直播中 / 未直播 / 未知 | 程序启动时为未知。"开始直播"成功后为直播中。每次"连接"成功后，真机适配器让命令行询问用户"设备现在是否正在直播"：输入 y 为直播中，输入 n 为未直播，其他任何输入（包括直接回车）为未知。没有交互终端时为未知。自动测试通过测试代码注入回答。模拟设备适配器不提问，直接报告自己内存中的状态。用户也可以随时用会话命令"直播已结束"把该字段改为未直播（见下） | 任一步结果为"未知"时 |
  | 直播参数 | 具体值 / 未知 | "设置直播参数"成功后为所设的值 | 每次"连接"成功后重置为未知。未知不妨碍重新设置 |
  因此断线之后的恢复路径是：执行"连接"，回答一个关于直播状态的问题，再执行"连接 Wi-Fi"。只有"直播"字段未知而连接仍在时，用会话命令"直播已结束"即可恢复。
- **第一版如何结束直播**：第一版不承诺"停止直播"动作。直播由用户在相机上手动结束，之后在命令行输入会话命令"直播已结束"。这是命令行自身处理的固定命令，不经过大模型，只把"直播"字段改为未直播（标注为人工告知值）并写一条日志，"Wi-Fi"和"直播参数"字段保持不变，不需要重新连接。如果作业核实 node-osmo 可以停止直播，该动作在里程碑 2 开始前加入承诺的指令集，并同样列为不需要确认的动作。
- **凭据处理**：Wi-Fi 名称与密码、RTMP 推流地址与密钥只存在本地配置文件里（不入库），以名称引用，例如"默认网络""默认直播目标"。大模型只看到名称，日志只记录名称。屏蔽规则统一适用于四处：用户的原话、用户对澄清问题的回答（这两处在发送给大模型之前和写入日志之前都先屏蔽）、翻译结果、适配器返回内容（这两处在写入日志之前屏蔽）。屏蔽方式是把与配置中任一凭据值完全相同的字符串替换为带配置名称的占位符（例如把真实的 Wi-Fi 名称替换成"默认网络"对应的占位符），这样大模型仍能把它对应到配置名称。只做整串精确匹配，长度不足 4 个字符的值不参与屏蔽，以免误伤普通词语。这只能挡住已登记在配置里的凭据；用户在话里输入一个未登记的密码时无法识别，因此命令行启动时显示一行提示：不要在输入中包含密码或密钥。
- **日志**：每条用户输入对应一行 JSON，追加写入本地 `logs/` 目录下按日期命名的文件（该目录不入库）。字段：时间、原话、所用模型、翻译结果、每一步的校验结论、是否经过人工确认、每一步的执行结果、澄清的问题与回答、执行前后每个状态字段的值及其来源（推算值或人工告知值）。第一版不做自动清理。
- **测试分两类**：
  - 确定性测试：校验规则、推演状态、失败处理、日志、模拟设备。翻译环节用固定的预置结果替身，不调用任何模型。只有这一类在 CI 上运行。
  - 翻译评测：按需手动运行，调用真实模型，不进 CI。评分方式见"Success Criteria"。
- **能力清单单一来源**：每个适配器的能力清单是一份数据定义（动作名、参数及取值范围、是否需要确认、依赖和改变哪些状态字段）。交给大模型的工具定义和校验层的规则都从这一份定义生成，不分别手写，避免两处不一致。
- **只看不做模式**：命令行支持一个"预演"开关。打开后照常翻译和校验，显示计划和每一步的校验结论，但不执行任何一步，日志标注为预演。
- **日志重放**：提供一个命令，读取某一条日志，把其中的翻译结果在模拟设备上重新校验和执行，用于事后排查。重放不调用模型，不连接真机。
- **模拟设备适配器**：在内存里模拟一台相机的状态，行为与 Pocket 3 适配器的能力清单一致。全部内核逻辑的自动测试都跑在它上面，不需要硬件。
- **模拟设备的能力清单是暂定的**：先按上方能力表中"有文档依据"的五个动作编写，作业结果出来后按真机实际情况修订。
- **Pocket 3 适配器**：对 node-osmo 的薄封装。第一版只承诺"有文档依据"的五个动作：连接（含配对）、连接 Wi-Fi、设置直播参数、开始直播、读取电量。停止直播、本地录像、状态读回在作业中核实，可行再加入。
- **真机测试的接收端**：在发起人本地电脑上运行一个开源 RTMP 服务器，Pocket 3 与电脑在同一个局域网内，推流到这台电脑。不使用任何公网直播平台。

## Success Criteria

- 翻译评测：一组 30 句预先写好的测试语句，每句配一份预期计划。用配置中指定的同一个模型、固定参数连续跑 3 轮，计划与预期完全一致才算对，每一轮都至少对 27 句（30 × 90%）。评测报告写明模型名称和日期。
- 越界语句 5 句（清单外动作、超范围参数）：到达适配器的越界指令数为 0，每句都给出拒绝原因。
- 歧义语句 5 句（含糊指代、缺少必要参数）：每句的结果都是"需要澄清"或"无法执行"，没有任何指令被执行。
- 以上 10 句属于同一次按需翻译评测，使用同一个模型、同样跑 3 轮，每一轮都必须全部通过。
- 每次执行都有一条完整日志，能从日志还原"用户说了什么、系统理解成什么、为什么放行或拒绝、设备返回了什么"。
- 真机上：node-osmo 实际支持的每一类指令，至少各有一次从一句话到 Pocket 3 做出反应的成功记录。
- 至少有一位发起人之外的人，在没有指导的情况下用过一次，并记录下他们卡在哪里。这次试用使用模拟设备适配器；发起人给这位试用者仓库访问权限和一个通过环境变量提供的模型密钥，不需要真机。

- 命令与名称。可执行程序名为 nlctl，由 package.json 的 bin 字段提供；仓库用 engines 字段和 .nvmrc 固定 Node.js 的当前长期支持版本。命令：`nlctl`（交互会话）、`nlctl run "<句子>"`（一次性执行一句话）、`nlctl run-plan <计划文件.json>`（不经过大模型，直接提交一份计划）、`nlctl replay <条目编号>` 与 `nlctl replay --last`、`nlctl log list`（列出最近的条目编号、时间、结局）、`nlctl init`（写出带注释的配置模板）。参数：`--adapter mock|pocket`（默认 mock，真机必须显式选择）、`--demo`、`--dry-run`、`--yes`（仅在 --demo 加 mock 时有效）、`--json`、`--config <路径>`。环境变量：NLCTL_MODEL_API_KEY（模型密钥）、NLCTL_CONFIG（配置路径）。npm 脚本 `npm run demo` 等价于 `nlctl --demo`。验证：确定性测试对每个命令和参数断言 --help 中有对应条目和一个示例。
