# Design: 自然语言设备控制内核（第一版：Osmo Pocket）

- 来源：`/office-hours`（2026-11-12）起草，`/autoplan`（2026-11-12）评审
- 仓库：rogerzhuuva/office
- Status: APPROVED（发起人于 2026-11-12 在最终关口回复 `as-is`）
- 本文件是合并后的定稿。评审全过程、被取代的旧说法和历史审阅意见存档在 `docs/designs/archive/2026-11-12-nl-device-control-kernel-review-record.md`。

## 1. 问题与定位

发起人希望公司有一个统一的软件平台，接入大疆设备和基于 ROS2 的机器人，并能接入 CV 模型和大模型 API，之后在内部推广或商用，并争取产生专利。

第一版把范围收窄为一个功能：**用户输入一句话，系统把它变成设备指令并安全地执行。** 平台是从这个功能里抽出来的结构，不是第一版的交付物。

- **定位**：可防守的部分是独立的校验层加审计，以及对没有官方 SDK 的设备的适配。把话翻译成工具调用是可替换的通用件。
- **第一版的性质**：它是校验层的试验台，不主张自然语言在几个动作的规模上优于固定命令。
- **需求证据**：目前没有。唯一确定的用户是发起人本人。

## 2. 约束与已核实的事实

- 发起人所在地区限飞无人机，第一版不依赖真机飞行。
- 发起人决定以 Osmo Pocket 3 为第一验证载体，Pocket 4 为第二种机型。
- Pocket 系列没有官方 SDK，通过开源逆向库 node-osmo 走蓝牙。
- 蓝牙必须在靠近设备的电脑上使用，真机联调只能在发起人本地进行。

**node-osmo 的实际接口**（依据：仓库 `examples/connect-to-device.js` 和 README，2026-11-12 读取；未读源码，未做真机测试）：

| 一次调用完成连接、加入 Wi-Fi、设置参数和开播：`startLiveStream(Wi-Fi 名称, Wi-Fi 密码, 推流地址, 分辨率, 帧率, 码率, 防抖)` | 示例代码中出现 |
| 读取电量百分比 | README 功能列表中有，调用方式未知 |

## 3. 前提

1. 先做插件，不先做平台。
2. 不重造轮子。自己写的只有翻译与校验层，以及现有方案没覆盖的设备适配。
3. 大模型不直接驱动设备，每条指令都经过独立的校验层。这个思路本身是公开做法，不构成专利点；专利目标保持现状，本版不做安排。
4. 以 Osmo Pocket 3 为第一验证载体（发起人决定）。
5. 先内部用，商用推迟到有第一个真实用户之后。

## 4. 架构

```
                    nlctl（命令行）
   会话 / run / run-plan / replay / scan / init / log list
        │ 一句话            │ 计划（不经模型）
        v                   │
   翻译前端 ──(计划)──────> v
   （大模型或预置结果）   ┌──────────────────────────────────────────┐
                          │ 内核入口：提交计划                        │
   提问入口 <────────────>│  结构校验 → 清单校验(推演状态) → 钩子     │
   （澄清/确认/状态告知， │  → 确认(非模拟设备只接受交互来源)         │
     提问前清空输入缓冲） │  → 决定行落盘 → 逐步执行 → 状态更新       │
                          │  → 结果行                                 │
                          └───────┬───────────────────┬──────────────┘
                 能力清单（单一来源，│                   │ 日志（独占锁、设备会话锁、
                 规范化哈希，按版本 │                   │ 屏蔽、崩溃文件）
                 保存）             v
                          适配器接口：清单、执行、状态事件、是否模拟
                            ├─ 模拟设备
                            └─ Pocket 适配器 ──> node-osmo（可选依赖，固定提交）──> 蓝牙
```

- **语言**：TypeScript + Node.js。node-osmo 是 TypeScript 库，同一语言直接调用。
- **内核入口**是一个接受"计划"并返回校验结论与执行结果的函数。翻译只是调用它的一个前端，以后加其他前端不需要改动校验、确认和日志。
- **隔离**：Pocket 适配器目录之外的代码不得导入 node-osmo，由构建检查保证。

## 5. 能力清单

每个适配器有一份数据形式的能力清单，是唯一来源。交给大模型的工具定义和校验规则都由它生成，不分别手写。

**每个动作的字段**

- 名称、说明。
- 种类：设备动作（调用适配器）或暂存动作（只改变内核保存的状态，不接触设备）。
- 参数列表。每个参数有名称、类型、必填或可选、可选时的默认值。类型为枚举、数值范围，或配置名称（允许取值是本地配置里该种类的全部名称）。
- 最少参数个数。
- 前置条件：状态字段到所要求取值的映射。
- 效果：状态字段到执行成功后取值的映射，可以引用一个或多个参数。
- 是否需要人工确认。

适配器可以附带一个纯函数形式的校验钩子，用于清单表达不了的约束（例如分辨率与帧率的组合）。钩子不得有副作用，不得调用模型。

**Pocket 清单的暂定形状**（读完 node-osmo 源码后定稿，见第 13 节）

| 动作 | 种类 | 参数 | 前置条件 | 效果 | 确认 |
|---|---|---|---|---|---|
| 选择网络 | 暂存 | 网络（配置名称；只有一个时可省略并取默认） | 无 | 网络=所选名称 | 否 |
| 设置直播参数 | 暂存 | 分辨率、帧率、码率、防抖；都可选，至少给一个 | 直播=未直播 | 只更新给出的子值 | 否 |
| 开始直播 | 设备 | 直播目标（配置名称；只有一个时可省略并取默认） | 网络已选择、直播=未直播 | 直播=直播中 | 是 |
| 读取电量 | 设备 | 无 | 无 | 无；返回百分比 | 否 |

- 暂定参数取值（实现前对照库的源码修订）：分辨率 480p、720p、1080p；帧率 25、30；码率 2 到 20 Mbps 的整数；防抖 关闭、RockSteady、RockSteady+、HorizonBalancing、HorizonSteady。
- "开始直播"把已暂存的网络、参数连同直播目标一次交给库。它失败或结果未知时无法区分是哪个内部阶段出了问题，统一记为这一步的失败或未知，并附库返回的原文。
- 是否保留独立的"连接"动作，取决于库是否提供单独的连接方法。不提供则没有这个动作。
- 停止直播、本地录像、状态读回是否加入第一版，在里程碑 2 开始前根据源码记录和真机测试结果一次决定；未加入的留到第一版之后。
- 模拟设备不另写清单，直接使用 Pocket 的这一份。Pocket 3 和 Pocket 4 共用一份清单，内容是通过测试的各台设备上都可用的动作的交集。
- 清单的哈希基于规范化的序列化结果。会话启动时把当前清单按哈希保存到日志目录下，供重放加载并校验。

## 6. 翻译

大模型拿到的是：由清单加本地配置名称生成的工具定义，以及当前状态的摘要（与决定行里记录的执行前状态相同）。翻译的结果只有四种：

1. **计划**：有序的步骤列表，每步是动作加参数。一句话可以对应多步，最多 10 步。
2. **需要澄清**：附一个问题。澄清最多一轮，第二次仍需澄清按"无法执行"处理。澄清的回答恰好等于某个会话命令时，按会话命令处理并退出澄清。
3. **无法执行**：附原因。
4. **翻译失败**：模型接口报错、超时、返回为空或格式不合法、缺少密钥。附原因，不执行任何一步。

缺少必填参数时由内核处理，不依赖大模型：内核给出固定格式的问题并列出该种类全部配置名称，这算作唯一的一轮澄清。

模型在配置里指定（服务方、接口地址、固定参数），可替换。输入长度上限暂定 500 个字符，超长直接拒绝，不交给模型。

## 7. 校验与确认

校验层是纯代码，不调用模型。

- **计划是不可信输入**，无论来自大模型还是 run-plan 文件：按严格结构校验，出现未知字段即拒绝；拒绝原型污染类的键名；数值必须是有限数且类型正确；最多 10 步；计划文件最大 64 KB。
- **先全部校验，再执行**：每一步都在推演状态上校验（从当前状态出发，逐步套用前面各步的效果）。任何一步不通过，整个计划都不执行，并说明是哪一步、为什么。
- **由清单生成的检查**：动作在清单内；参数在取值范围内；最少参数个数；前置条件；是否需要确认。
- **固定规则**：先全部校验再执行；规则所依赖的字段为未知时拒绝，并告诉用户如何确定该字段；澄清最多一轮；配置名称类参数在只有一个名称时取默认；最少参数个数。
- **确认**：目前只有"开始直播"需要，因为它把画面发到设备之外。
  - 时机：整个计划通过校验之后、任何一步执行之前，只问一次。
  - 提示内容：完整的步骤列表；直播目标的名称和主机地址（不显示密钥）；目标不是本机或局域网地址时加一行醒目提示；清单里没有"停止直播"时加一句"本工具目前无法停止直播，需要在相机上手动结束"。
  - 提问前先丢弃输入缓冲里已有的内容。输入 y 才执行，其他任何输入记为用户拒绝，整个计划不执行。
- **真机必须有人确认，由内核保证**：每个适配器声明自己是否为模拟设备。对非模拟设备，内核入口拒绝任何非交互的确认来源。预先同意参数 `--yes` 只在演示模式加模拟设备时有效。
- **没有交互终端时**，任何需要人回答的地方（确认、设备是否正在直播）统一报 NEEDS_TTY，不执行该计划。因此在真机上只有在交互终端里才能开播，无人值守时只能预演。

## 8. 执行与状态

- 步骤按顺序执行。适配器对每一步返回成功、失败（附原因）或未知（超时、断连、被中断），可以带一个返回值（例如电量）。
- 不自动重试，不回滚。某一步失败或未知时停止后续步骤，并告诉用户哪些已生效、哪一步出了问题、哪些没有执行。
- 超时按动作在本地配置里设置，默认 10 秒（暂定，真机测出实际耗时后修订）。配置里的动作名在启动时对照清单检查。超时或中断之后才到达的回调一律丢弃。
- 结果为未知时，适配器主动断开蓝牙连接。
- 会话在一个条目执行完并写入结果行之前，不读取下一条输入。执行中按 Ctrl-C：当前步骤记为未知，停止后续步骤，照常写结果行。

**状态**由内核持有。第一版假定无法从设备读回状态（电量除外）。

| 字段 | 取值 | 说明 |
|---|---|---|
| 网络 | 所选的配置名称 / 未选择 | 由"选择网络"设置；只有一个网络时取默认 |
| 直播参数 | 四个子值，各自为具体值或未设置 | 由"设置直播参数"更新给出的子值 |
| 直播 | 直播中 / 未直播 / 未知 | 程序启动时为未知 |
| 连接 | 已连接 / 未连接 | 仅当库提供独立的连接方法时才有 |

- 字段的值按三层依次确定：清单里动作的效果，然后是用户告知的值，最后是设备报告的值。设备报告的值优先；两者冲突时取保守的一方（直播中）。日志标注每个字段的来源。
- 适配器可以通过状态事件通道向内核报告设备主动断开等变化；库没有事件则不用。
- "直播"字段未知时，在第一次"开始直播"之前由适配器提供的问题询问用户设备是否正在直播（y 为直播中，n 为未直播，其他为未知）。模拟设备不提问，直接报告自己内存中的状态。
- 第一版不承诺停止直播。直播由用户在相机上手动结束，然后输入会话命令"直播已结束"，它只把"直播"字段改为未直播。
- 退出会话时如果"直播"是直播中或未知，提示用户相机可能仍在直播。

## 9. 日志与重放

- 位置：本地日志目录（默认相对于配置文件所在目录，不入库），按日期分文件。文件以仅本人可读写的权限创建。第一版不做自动清理。
- **每个条目两行**，共用一个条目编号，格式为日期加当日序号（例如 20261112-0007）；两行都写入编号日期对应的文件。
  - 决定行，执行前写入并先刷到磁盘：格式版本、时间、条目编号、会话标识、nlctl 版本、原话、模型、适配器、清单哈希、翻译结果、澄清的问题与回答、填入默认值后的计划、每一步的校验结论、是否预演、是否重放及来源条目、确认的回答、执行前各状态字段的值及来源。
  - 结果行，执行后写入：条目编号、结局、每一步的结果及返回值、执行后各状态字段的值及来源、所连接设备的型号和固件版本（能读到时）。
- 决定行写入失败则不执行任何一步。只有决定行没有结果行，表示被中断；启动时只把不属于任何仍在运行的会话的未完成条目报告为被中断。
- **结局**在代码里只定义一处：已执行、部分执行、执行失败、校验拒绝、用户拒绝、无交互终端、需要澄清后未执行、无法执行、翻译失败、会话命令。预演和重放的标记在决定行里，这两类条目的结局报告校验的结果。
- **锁**：日志锁用独占创建的方式获取，最多等待 3 秒，超时报 LOG_LOCKED。每台设备另有一把会话锁，同一台设备同时只允许一个会话驱动。读取日志时容忍最后一行不完整。
- **凭据屏蔽**：需要屏蔽的只有密码、推流密钥、带密钥的完整推流地址（含拼接和 URL 编码形式）、模型密钥和鉴权头。网络名称和直播目标名称不屏蔽。
  - 按子串匹配，先替换最长的；长度不足 8 个字符的秘密不参与，并在启动时按名称列出。
  - 作用于：发给大模型的文本、日志中的自由文本字段、错误输出、崩溃文件、截获的第三方库输出。请求头永不写入日志。
  - 只能挡住已登记在配置里的秘密，所以启动时提示不要在输入中包含密码或密钥。
- **预演**：照常翻译和校验并显示结论，不执行任何一步，不改变状态；仍显示澄清问题；不显示确认提示，只标明哪些步骤在真实执行时需要确认。
- **重放**：按条目编号选择。只有翻译结果为"计划"的条目可以重放；按条目记录的哈希加载当时的清单并校验哈希；把内核状态和模拟设备内存设置为记录的执行前状态；原样注入记录的确认回答；比较每一步的校验结论。重放不调用模型，不连接真机，自己也写一条标记为重放的条目，且该条目不可再重放。

## 10. 命令行界面

可执行程序名为 `nlctl`。仓库用 `engines` 字段和 `.nvmrc` 固定 Node.js 的当前长期支持版本。第一版支持 Linux 和 macOS，不支持 Windows。

| 命令 | 作用 |
|---|---|
| `nlctl` | 交互会话。标准输入不是终端时逐行按 run 处理，退出码取第一个非零值 |
| `nlctl run "<句子>"` | 一次性执行一句话 |
| `nlctl run-plan <文件>` | 不经过大模型提交计划；文件可以包含多份计划，在同一进程里依次提交 |
| `nlctl replay <条目编号>` / `--last` | 重放 |
| `nlctl log list` | 列出最近的条目编号、时间、结局 |
| `nlctl scan` | 列出发现的设备的标识、名称和机型 |
| `nlctl init` | 写出带注释的配置模板 |

- 参数：`--adapter mock|pocket`（默认 mock）、`--demo`、`--dry-run`、`--yes`（仅 `--demo` 加 mock）、`--json`、`--config <路径>`。
- 环境变量：`NLCTL_MODEL_API_KEY`、`NLCTL_CONFIG`。
- 会话命令（不经过大模型，去掉首尾空白后完全相同才算）：帮助 / help；状态 / status；直播已结束；预演 开 / 预演 关；退出 / exit / quit。输入与三个字符以上的命令只差一两个字符时，提示"是否想输入某某"。每个条目完成后显示它的编号。
- 每个 run 或 run-plan 进程从初始状态开始。
- **真机配置**：必须在配置里写明设备标识和机型，不自动连接发现的设备。第一次对某个设备标识执行设备动作前，显示其标识和名称并要求确认一次。来自蓝牙的名称和机型文本在显示和记录前去掉控制字符。
- **演示模式**：零配置，不需要模型密钥，只连接模拟设备，内置一个网络和一个直播目标，使用预置的翻译结果，启动时列出演示句子。输入不在列表里的句子时列出可用句子并说明自由输入需要密钥。示例句子"用 1080p、30 帧开始直播"作为第一句输入时，结局必须是已执行。
- **默认安装不需要蓝牙工具链**：node-osmo 是可选依赖，固定到具体提交，只在选择 pocket 适配器时加载。
- 启动信息显示适配器、模式、模型、日志路径、会话命令和不要输入密码的提示。非演示模式在启动时检查配置和模型密钥。

## 11. 错误码

错误输出格式统一：第一行是哪个操作因为什么值失败，加括号里的错误码；随后按需给出原因、是否已对设备产生动作、上下文（nlctl 和 Node 版本、操作系统、适配器、模型、配置路径、相关环境变量的名称、底层错误原文）；最后一行是修复办法。错误写到标准错误输出，加 `--json` 时输出同样字段的 JSON。意外异常不打印调用栈，写入崩溃文件并打印其路径。错误码页和结局列表由代码生成。

| 错误码 | 何时 | 退出码 | 修复办法 |
|---|---|---|---|
| USAGE | 参数错误或组合不允许 | 2 | 正确的用法示例 |
| CONFIG_MISSING | 非演示模式找不到配置文件 | 3 | 运行 `nlctl init` |
| CONFIG_INVALID | 配置格式错误，或超时配置里的动作名不在清单内 | 3 | 指出键名，不显示值 |
| MODEL_KEY_MISSING | 非演示模式缺少模型密钥 | 3 | 设置环境变量，或加 `--demo`，或改用 `run-plan` |
| INPUT_TOO_LONG | 输入超过长度上限 | 4 | 写明上限和实际长度 |
| PLAN_REJECTED | 计划未通过校验 | 4 | 允许的取值，或下一步该输入什么 |
| CANNOT_EXECUTE | 无法执行，或澄清超过一轮 | 4 | 原因和可用动作 |
| NEEDS_TTY | 需要人回答但没有交互终端 | 5 | 在交互终端里运行；真机有意不提供预先同意；`--dry-run` 可无人值守预览 |
| TRANSLATE_FAILED | 模型接口报错、超时、空或格式不合法 | 6 | 未对设备产生动作，可重试；附状态码和请求编号 |
| STEP_FAILED | 某一步被设备拒绝 | 7 | 已生效、出错、未执行的步骤 |
| STEP_UNKNOWN | 某一步超时、断连或被中断 | 8 | 设备状态未知及恢复步骤 |
| BT_OFF / BT_PERMISSION / BT_DRIVER_MISSING | 蓝牙关闭、未授权、可选依赖未安装 | 9 | 对应操作系统的做法 |
| DEVICE_NOT_FOUND / DEVICE_BUSY | 找不到配置的设备、设备被另一个会话占用 | 9 | 运行 `nlctl scan`；或结束另一个会话 |
| LOG_WRITE_FAILED / RESULT_WRITE_FAILED / LOG_LOCKED | 决定行写入失败、结果行写入失败、取不到锁 | 10 | 路径和系统错误；结果行失败时把结果打印出来并把状态标为未知 |
| REPLAY_NOT_FOUND / REPLAY_MANIFEST_MISSING / REPLAY_NOT_REPLAYABLE | 条目不存在、清单文件缺失、条目类型不可重放 | 11 | 运行 `nlctl log list` |
| REPLAY_MISMATCH | 重放结论与原条目不一致 | 12 | 不一致的步骤 |
| EVAL_FAILED | 评测有一轮未达标 | 13 | 未通过的句子 |
| USER_DECLINED | 确认时未输入 y | 14 | 无 |

## 12. 测试

- **确定性测试**（在 CI 上运行，Linux 和 macOS，不调用模型，不需要密钥和硬件）：翻译环节用预置结果替身。覆盖范围见测试计划。重点：
  - 对校验器做基于属性的随机测试：任意生成的计划只有在完全合法时才会到达适配器。
  - 直接调用内核入口，给非模拟的测试适配器注入自动同意，断言被拒绝。
  - 决定行刷盘先于执行；写入失败不执行；执行中途异常时只有决定行。
  - 适配器一致性套件，同时跑在模拟设备和伪造的 node-osmo 层上，含故障注入（失败、未知、执行中断开、空闲时断开、迟到的响应）。
  - 日志在跨零点、末行不完整、两个会话并发、磁盘写满四种情况下的行为。
  - 演示模式第一句话结局为已执行；不装可选依赖时安装并跑通演示。
  - 每个错误码的输出含错误码和修复办法，且不含任何已配置的秘密。
- **翻译评测**（按需手动运行，调用真实模型，不进 CI）：40 句全部在模拟设备上运行，每句注明起始状态和本地配置；评测在校验之后停止，不执行。
  - 30 句配预期计划，比较的是填入默认值之后的计划，完全一致才算对。
  - 5 句越界语句，通过条件是最终结果为拒绝或无法执行。
  - 5 句歧义语句，通过条件是需要澄清或无法执行。
  - 同一个模型、固定参数连续跑 3 轮，每轮 30 句中至少对 27 句，另外 10 句全部通过。报告写明模型和日期。
- **真机测试**：手动，按第 13 节的记录模板。
- 测试计划存放在 gstack 的项目目录下，供 `/qa` 使用。

## 13. 里程碑与构建顺序

**开工前**

1. 读 node-osmo 源码，写一页记录：实际提供的方法和参数、有没有停止直播、电量如何获取、有没有状态或断开事件、机型取值。然后定稿第 5 节的清单形状。这一步先于内核实现。
2. 用不超过一天核查：校验层能否作为保护层放在 ROSA、RAI 或 ROS-MCP 之下。只记录结论和依据。
3. 交付真机测试脚本、一页准备说明和记录模板。

**里程碑 1：内核 + 模拟设备。** 文字输入到模拟设备执行的完整链路，含第 5 到 12 节的全部内容和文档。可在云端完成。构建次序：内核主流程和模拟设备在前；日志的两行写入、加锁和屏蔽从第一天接入主流程；重放和清单按版本保存排在第一次外部试用之后。

**里程碑 2：真机适配器。** 在发起人本地联调。"通过"指某台设备在真机测试中开始直播成功。

- 两台都通过：以 Pocket 3 为主，Pocket 4 一并支持。
- 只有一台通过：只支持那一台。
- 两台都不通过：有第二台不同操作系统的电脑则换机重试一次；仍不通过则取消里程碑 2，把里程碑 4 提前并固定为 ROS2 仿真适配器，届时需要发起人重新确认。
- 通过的设备上某个动作失败，则把它从清单中移除。
- 逆向协议用于商用的合规性，在里程碑 2 开始前取得法务答复；答复之前产出只用于内部演示。

**里程碑 3：语音输入。** 前端加语音转文字。

**里程碑 4：第二种设备。** ROS2 仿真或行业无人机，验证适配器接口可扩展。

并行方式：开工前三项先做。之后内核与 Pocket 适配器可以并行，两者共用的适配器接口类型由内核一侧先定稿。命令行在内核接口确定后开始，文档最后。
